# 1. 项目概述

## 1.1 项目背景

本平台面向学校教学与学习场景，将个人资料管理、课程管理、教学资源建设、AI 文档处理、在线练习与考试、课程互动和教学分析整合为统一的软件系统。平台以教学资料为基础，以统一 AI 服务能力为支撑，形成资料处理、知识沉淀、课程共享、教学活动和学习反馈的业务闭环。

## 1.2 建设范围

- 建设统一的校级用户、组织、角色和权限体系。

- 提供个人资料库、院系资料共享和课程资源管理能力。

- 集成七类 AI 智能工具，并提供统一 AI 任务管理能力。

- 提供课程创建、加入审核、教学资源、作业、考试、练习和成绩管理。

- 提供课程讨论、师生问答、公告通知和教学计划。

- 提供学生学习分析、教师课程分析及教学管理统计。

- 提供统一文件存储、搜索、消息、日志、导出和系统配置等公共能力。

## 1.3 建设边界

平台定位为教学资料处理与教学协同平台。AI 输出属于辅助内容，正式教学资源发布、重要成绩确认和关键教学管理操作仍需遵循人工审核或业务确认规则。平台不应将 AI 自动生成结果直接视为权威教学结论。

# 2. 产品定位与建设目标

## 2.1 产品定位

面向全校教师、学生、管理员和教学管理人员，构建统一的教学资料智能处理与知识服务平台。通过统一身份、统一资料中心、统一 AI 引擎和统一课程教学服务，支持教学资料数字化处理、知识资源沉淀、教学活动协同与学习过程分析。

## 2.2 建设目标

- 统一入口：全校用户通过统一 Web 平台访问授权功能。

- 统一资料：个人资料、院系共享资料和课程资料建立清晰的归属与授权关系。

- 统一 AI：模型、提示词、解析、检索和任务执行能力集中管理。

- 教学闭环：课程、资源、知识点、习题、作业、考试、成绩和学习分析相互关联。

- 权限可控：依据角色、组织范围、课程成员关系和资源授权实施访问控制。

- 可持续扩展：采用模块化单体，降低初期运维复杂度，同时保留后续服务拆分能力。

# 3. 用户角色与权限设计

| **角色**     | **主要职责**                                                          | **典型权限范围**                                                 |
|--------------|-----------------------------------------------------------------------|------------------------------------------------------------------|
| 教师         | 课程建设、教学资源管理、AI 内容审核、作业考试管理、成绩管理、课程互动 | 本人创建或获授权管理的课程；本人资料；获授权院系资源             |
| 学生         | 加入课程、学习资料、AI 辅助学习、练习、作业、考试、讨论               | 本人资料；已加入课程中授权开放的资源和活动；本人学习记录         |
| 管理员       | 账号与组织管理、角色权限、模型配置、系统参数、日志与运行维护          | 平台系统管理范围；不因管理员身份而默认读取私人问答和私人资料正文 |
| 教学管理人员 | 教学计划监督、院系课程统计、资源建设统计、教学活动分析                | 被授权学校或院系范围内的管理数据；原则上以汇总数据为主           |

## 3.1 注册与账号规则

- 平台支持用户自主注册。

- 自主注册不代表用户可以自行获得教师、管理员或教学管理人员权限。

- 普通注册账号的默认角色、教师身份核验、学生身份核验及审核流程需在详细设计阶段确定。

- 管理员和教学管理人员角色只能由有权人员分配。

- 支持一个账号拥有多个业务角色；同一用户在不同课程中可以具有不同的课程身份。

- 账号停用、密码重置、登录会话撤销和重要身份变更应留有审计记录。

## 3.2 权限模型

采用 RBAC 角色权限控制，并叠加数据范围权限和资源访问权限。菜单权限仅用于前端展示，后端接口必须执行真实授权检查。

- 角色权限：决定用户可以执行哪些操作。

- 组织范围：决定用户可以管理或查看哪些学校、院系、专业及班级数据。

- 课程范围：依据课程成员关系、教师管理身份和课程状态授权。

- 资源范围：依据文件所有者、共享范围、课程关联和资源发布状态授权。

- 个人隐私：学生个人资料、个人问答和私人学习记录不得因院系管理或系统管理身份而默认开放。

## 3.3 资料共享规则

| **资料类型** | **默认规则**                     | **补充说明**                                     |
|--------------|----------------------------------|--------------------------------------------------|
| 教师资料     | 默认个人私有；教师可选择院系共享 | 院系共享不等于全校公开                           |
| 学生资料     | 默认个人私有                     | 学生主动授权或按课程规则提交后才可被相应对象访问 |
| 教学管理资料 | 按授权范围管理                   | 可面向指定院系或课程发布                         |
| 正式教学资源 | 按发布范围访问                   | 发布、撤回、版本和审核状态需可追溯               |

## 4.1 AI 七大工具的业务边界

| **工具**      | **主要输入**                         | **主要输出与规则**                                   |
|---------------|--------------------------------------|------------------------------------------------------|
| 文档智能问答  | 用户问题、用户有权访问的文档或知识库 | 带资料来源引用的回答；不得检索未授权资料             |
| 知识点提取    | 课程资料、文档章节                   | 结构化知识点、层级和来源位置；进入正式资源库前需审核 |
| 习题智能生成  | 知识点、章节、难度、题型要求         | 题目、选项、答案、解析等结构化内容；教师审核后发布   |
| 资料智能检索  | 关键词或自然语言查询                 | 关键词、语义或混合检索结果；返回前再次验证权限       |
| PPT 内容提取  | PPT 文件                             | 逐页文本、结构化提纲和摘要                           |
| Word 教案整理 | Word 文档或教学素材                  | 教案结构、教学目标、重难点和整理结果                 |
| PDF 智能标注  | PDF 文件                             | 重点内容、批注建议、页码或文本位置；保留原文件       |

## 4.2 课程与考试规则

- 课程加入支持邀请码和申请审核两种方式。

- 习题支持自由练习和教师布置两种使用方式。

- 考试支持练习式与正式考试式两种模式，具体考试规则在课程教学详细设计中配置。

- 题库题目、发布试卷和学生答题记录应关联题目版本。

- 考试发布后固定试卷版本，题库后续修改不得改变已发布考试内容。

- 客观题可自动判分；主观题可由教师人工批改，AI 仅提供辅助评分建议。

- 成绩正式公布前由教师按业务规则确认；成绩修改应保留修改记录。

# 5. 核心业务流程

## 5.1 教师资料处理与发布

1.  教师登录，选择个人资料库或课程资料入口。

2.  上传文件，Java 校验身份、文件类型、大小和目标资料范围。

3.  文件写入 RustFS，MySQL 保存文件元数据和归属关系。

4.  根据处理需求创建解析或 AI 任务，并通过 RabbitMQ 投递。

5.  Python Worker 读取授权文件，执行解析、知识提取或习题生成。

6.  AI 结果返回 Java，保存为草稿或待审核内容。

7.  教师审核、修改或退回；审核通过后按个人、院系或课程范围发布。

8.  发布事件触发搜索索引更新和相关通知。

## 5.2 学生学习流程

9.  学生注册并完成必要身份验证。

10. 通过邀请码或申请审核加入课程。

11. 查看本人有权访问的课程资料和知识点。

12. 使用文档问答、资料检索等 AI 工具辅助学习。

13. 参加自由练习、教师作业或考试。

14. 提交答案，系统按题型执行自动判分或进入人工批改流程。

15. 形成成绩、错题和学习分析记录。

## 5.3 AI 异步任务流程

16. 前端向 Java 提交 AI 任务请求。

17. Java 校验用户身份、资料权限、任务类型和参数。

18. Java 在 MySQL 创建任务记录及待投递事件。

19. 可靠消息发布程序将任务投递至 RabbitMQ。

20. Python Worker 消费任务并执行文档解析、检索或模型调用。

21. Python 保存允许由其管理的处理结果，并通过结果消息或受保护接口回传状态和结果引用。

22. Java 校验结果并更新正式业务状态。

23. 前端通过 SSE 或轮询获取进度和最终结果。

## 5.4 作业与考试流程

24. 教师创建作业或考试，选择题目并配置时间、规则和适用对象。

25. 系统固定题目版本并发布。

26. 学生在允许时间内答题，系统定期保存答题进度。

27. 学生提交或考试到时自动交卷。

28. 系统自动判定客观题，主观题进入人工批改或 AI 辅助评分流程。

29. 教师确认成绩并公布。

30. 系统更新学生错题记录和学习分析。

# 6. 总体软件架构

## 6.1 架构决策

| **架构维度** | **最终方案**                 | **说明**                                    |
|--------------|------------------------------|---------------------------------------------|
| 整体架构     | 模块化单体                   | Java 主业务应用统一部署，内部按业务模块隔离 |
| AI 计算      | 独立 Python 服务             | 承担 AI 模型调用、文档解析、RAG 和工作流    |
| 模块内部     | MVC + DDD 混合               | 普通模块简化分层，复杂模块建立领域边界      |
| 模块通信     | 公开服务接口 + 领域/应用事件 | 禁止跨模块随意访问内部实现                  |
| 异步通信     | RabbitMQ                     | 处理可靠异步任务和业务事件                  |
| 部署         | Docker Compose 起步          | 按资源和生产要求再扩展部署形态              |

## 6.2 五层逻辑结构

| **层次**   | **主要内容**                                                            |
|------------|-------------------------------------------------------------------------|
| 用户访问层 | 教师、学生、管理员、教学管理人员；响应式 Web                            |
| 业务应用层 | 用户组织、资料、AI、课程、教学资源、教学学习、互动、分析、系统管理      |
| 公共服务层 | 认证授权、文件服务、AI 调度、文档解析、知识检索、任务、通知、审核、导出 |
| 基础设施层 | MySQL、Redis、Elasticsearch、Milvus、MongoDB、RabbitMQ、RustFS          |
| 运行部署层 | Docker、Nginx、配置、日志、监控、备份、安全审计                         |

以上为逻辑分层，不意味着每一层必须部署为独立服务。Java 业务模块初期仍属于一个模块化单体应用；Python AI 服务独立部署是由于运行环境、依赖和计算负载不同。

# 7. 模块边界与依赖规范

## 7.1 Java 业务模块

| **模块**            | **数据和职责归属**                              |
|---------------------|-------------------------------------------------|
| user / organization | 用户、角色、权限、组织层级及身份审核            |
| resource            | 文件元数据、分类、共享关系、版本及资源关联      |
| ai                  | AI 任务、模型配置、调用记录、结果接收和任务状态 |
| course              | 课程、成员、加入申请、课程状态                  |
| teaching-resource   | 知识点、习题、教学资源审核和发布                |
| teaching-learning   | 教学计划、作业、考试、试卷、答题和成绩          |
| interaction         | 讨论、提问、公告和消息                          |
| analytics           | 学习分析和教学统计                              |
| system              | 系统参数、运行管理、审计查询                    |

## 7.2 模块依赖规则

- 模块只能通过其他模块公开的应用服务、查询接口或事件访问其能力。

- 禁止直接调用其他模块的内部 Repository、Mapper 或 Domain Entity。

- 禁止跨模块随意写入其他模块拥有的业务表。

- 公共基础设施不得反向依赖具体业务模块。

- 复杂跨模块用例由应用层协调；异步后续动作通过事件或消息执行。

- 模块之间的数据关联通过明确的业务 ID 建立，避免共享可变对象。

## 7.3 推荐目录结构

普通 MVC 模块示例：

system/\n├── controller/\n├── service/\n├── mapper/\n├── entity/\n├── dto/\n└── configuration/

复杂 DDD 模块示例：

course/\n├── interfaces/\n├── application/\n│ ├── command/\n│ └── query/\n├── domain/\n│ ├── model/\n│ ├── service/\n│ ├── repository/\n│ ├── event/\n│ └── rule/\n└── infrastructure/\n ├── persistence/\n ├── mapper/\n └── repository/

# 8. 设计模式规范

| **设计模式**    | **应用场景**                              | **实施约束**                                                      |
|-----------------|-------------------------------------------|-------------------------------------------------------------------|
| 工厂模式        | AI 模型、文档解析器、导出器创建           | 存在多种实现且需要按配置创建时使用；优先结合 Spring 容器          |
| 策略模式        | 题型判分、模型选择、检索算法、通知渠道    | 算法可替换时使用；不要为单一固定实现过度抽象                      |
| 适配器模式      | 不同大模型厂商、RustFS/S3 SDK、外部服务   | 统一外部接口差异，业务层不直接依赖厂商 SDK                        |
| 观察者模式      | 作业发布、考试事件、AI 完成、资源发布通知 | 简单进程内事件可用 Spring Event；可靠异步流程使用 RabbitMQ        |
| 模板方法        | 文档处理和 AI 任务公共流程                | 固定公共步骤，差异步骤由子类或组合组件实现                        |
| 状态模式/状态机 | AI 任务、审核、作业、考试状态流转         | 通过明确状态转换规则限制非法状态变化                              |
| 仓储模式        | 业务数据访问                              | MyBatis Mapper 负责持久化实现；复杂领域模块可定义 Repository 接口 |
| 责任链模式      | 上传校验、权限校验、内容安全检查          | 每个处理器单一职责，链路顺序可测试                                |
| 事务发件箱      | 业务事务与 RabbitMQ 消息一致性            | 业务数据和待发事件在同一 MySQL 事务中提交，再异步投递             |

## 8.1 统一依赖原则

- 优先使用 Spring 依赖注入管理对象，不滥用静态工厂和手动 new。

- Controller 负责协议接入和参数校验，不承载核心业务规则。

- 领域层不依赖 Web、数据库实现和大模型 SDK。

- 事务由应用服务或明确的业务边界管理。

- 耗时外部调用不得长期占用数据库事务。

- 设计模式必须解决真实变化点，不以模式数量作为代码质量指标。

## 9.2 前端规范

- 使用 Vue 3 Composition API 和 script setup。

- 使用 TypeScript 定义 API 请求、响应和页面模型类型。

- 按业务模块组织页面、API、组件、类型和 composables。

- 统一布局、导航、主题、表单、表格、弹窗和消息反馈组件。

- 前端菜单和路由按角色展示，但后端必须重新授权。

- 对移动端采用响应式布局，避免复杂后台页面在手机端简单缩放。

- 建议使用 ESLint、Prettier、Vitest 和 Playwright 作为质量工具。

## 9.3 Java 后端规范

- Spring Security 负责认证和授权；JWT 作为访问凭证方案，Refresh Token 需要有撤销和轮换设计。

- MyBatis 负责关系数据库访问；复杂 SQL 使用 XML 管理，避免业务 SQL 散落在 Controller。

- 核心业务事务使用 Spring 事务管理。

- 统一 DTO、Entity、Mapper/Repository 和异常响应规范。

- 业务模块不直接调用大模型厂商 API。

- 所有跨院系、跨课程和跨用户访问都进行数据范围校验。

## 9.4 Python AI 服务规范

- FastAPI 提供服务接口，Pydantic 负责输入输出校验。

- LangChain 用于模型、Prompt、文档加载和检索组件。

- LangGraph 用于确实需要状态、分支、重试或人工审核节点的复杂工作流。

- Python Worker 负责消费 RabbitMQ 中的 AI 任务。

- 模型供应商通过统一 Provider/Adapter 接口接入。

- Embedding 模型、聊天模型、重排序模型和 OCR 能力分别配置，不假定单一模型支持全部能力。

- AI 结果返回 Java 后，由 Java 执行业务校验和正式业务数据写入。

# 10. 数据架构与数据归属

| **组件**      | **权威数据/用途**                                                               | **不应承担的职责**                     |
|---------------|---------------------------------------------------------------------------------|----------------------------------------|
| MySQL         | 用户、权限、组织、课程、资料元数据、习题、作业、考试、成绩、审核、AI 任务主记录 | 不作为全文搜索引擎                     |
| Redis         | 缓存、限流、短期状态、幂等键、锁和会话辅助                                      | 不作为成绩或任务的唯一持久来源         |
| Elasticsearch | 全文索引、关键词搜索、文档段落索引                                              | 不作为权限和正式业务数据的唯一来源     |
| Milvus        | 文档片段和知识内容的向量索引                                                    | 不作为原始文件或正式业务记录的唯一来源 |
| MongoDB       | 灵活结构的解析结果、复杂 JSON、部分工作流检查点                                 | 不替代 MySQL 存储核心关系型业务        |
| RabbitMQ      | 异步消息和任务投递                                                              | 不替代 MySQL 任务状态记录              |
| RustFS        | 原始文件、处理文件和导出文件对象                                                | 不直接承担业务权限和文件元数据管理     |

## 10.1 数据一致性原则

- MySQL 是正式业务事实来源；搜索和向量索引是可重建的派生数据。

- 文件对象写入 RustFS 后，MySQL 保存对象键、文件名、大小、类型、归属和状态。

- 索引更新应可重试；文件或资源撤回时应同步处理搜索和向量索引。

- 跨系统写入采用任务状态、事件记录和补偿机制，不假设多种数据库天然具备分布式事务。

- MongoDB 与 MySQL 间通过稳定业务 ID 关联，避免重复保存同一份权威业务数据。

## 10.2 Elasticsearch 与 Milvus 分工

Elasticsearch 负责关键词和全文检索；Milvus 负责语义向量检索。需要混合检索时，由检索服务分别获取候选结果，再执行去重、融合和必要的重排序。Embedding 模型版本变化时，需要规划向量重建和索引版本切换。

## 10.3 Milvus 元数据建议

- 文档 ID、文档版本、段落 ID。

- 课程 ID、院系 ID、资料所有者 ID。

- 页码、章节、内容类型。

- Embedding 模型标识和向量版本。

- 必要的访问范围过滤字段。

向量元数据过滤只能作为检索优化。最终访问授权必须回到 Java 权限服务和 MySQL 中的真实授权关系校验。

# 11. Java 与 Python 协作设计

## 11.1 职责边界

| **Java 主业务后端**                    | **Python AI 服务**          |
|----------------------------------------|-----------------------------|
| 用户身份、角色和权限                   | 模型调用和 AI 工作流        |
| 课程、资源、作业、考试、成绩等正式业务 | 文档解析、切片和 Embedding  |
| AI 任务创建、授权检查和任务主状态      | RAG 检索、Prompt 和模型生成 |
| AI 结果校验、审核流转和正式保存        | AI 中间结果和处理过程       |
| 消息投递协调、业务事件和审计           | 执行 AI 任务并回报结果      |

## 11.2 通信方式

| **场景**                       | **通信方式**                             |
|--------------------------------|------------------------------------------|
| 快速问答、健康检查、轻量查询   | HTTP REST                                |
| 批量解析、批量生成、长时间任务 | RabbitMQ 异步任务                        |
| 任务结果回传                   | 结果消息或受保护的 Java 回调接口         |
| 前端进度展示                   | SSE 或轮询；根据任务实时性和部署条件确定 |

## 11.3 任务可靠性

- Java 先持久化任务和待发事件，再投递消息。

- 消费者采用手动确认或等效可靠确认机制。

- 任务消息携带唯一 taskId 和幂等标识。

- 失败任务按策略重试；超过阈值进入死信队列或人工处理队列。

- 重复消息不得重复创建正式资源或重复确认成绩。

- 任务应有超时、取消、失败原因和重试次数记录。

- Python 不直接写入 Java 业务模块的核心表。

# 12. 文件与对象存储设计

## 12.1 存储方案

文件对象存储确定采用 RustFS。Java 业务侧通过统一 FileStorageService 抽象访问 RustFS，底层使用 S3 兼容 API 或相应 SDK。业务模块不得将 RustFS 专有调用散落在课程、资料和 AI 模块中。

## 12.2 文件管理职责

- RustFS 保存文件对象。

- MySQL 保存文件 ID、对象键、原始名称、扩展名、MIME 类型、大小、所有者、所属院系、共享范围、版本和处理状态。

- Java 文件服务负责身份验证、授权、上传策略、下载授权和对象生命周期协调。

- Python 通过授权文件访问方式读取待处理文件，不绕过权限直接访问宿主机路径。

- Elasticsearch 保存可检索文本索引；Milvus 保存向量；MongoDB 可保存复杂解析结构。

## 12.3 文件访问安全

- 私有对象默认禁止匿名公开访问。

- 可采用短时预签名 URL，但必须先完成 Java 侧权限检查。

- 预签名 URL 有效期应尽量短，并避免写入普通日志。

- 文件名与对象键分离，对象键使用不可预测的唯一标识。

- 上传时检查文件类型、大小、扩展名与实际内容，必要时进行恶意文件扫描。

- 删除前检查课程资源、知识点、习题和 AI 任务等关联。

- 对关键资料保留版本、审计和备份策略。

## 12.4 RustFS 部署待定项

RustFS 已确定为对象存储实现，但 Bucket 划分、容量规划、纠删码或副本策略、访问域名、备份方式、生命周期规则及生产部署拓扑仍需结合服务器和运维条件确定。

# 13. 安全与隐私设计

## 13.1 身份与访问安全

- 密码使用安全的单向密码哈希算法保存，不保存明文密码。

- JWT 和 Refresh Token 设置有效期、轮换和撤销策略。

- 关键接口进行服务端角色和数据范围校验。

- 管理员、教师和教学管理人员的权限按职责最小化分配。

- 重要管理操作记录操作者、时间、目标对象和结果。

## 13.2 AI 数据安全

- AI 检索只能使用当前用户有权访问的资料。

- 向模型发送资料前执行授权检查和必要的数据最小化处理。

- 模型 API Key 加密或通过安全配置注入，绝不下发前端。

- AI 对话和处理日志遵循必要性原则，避免无条件保存敏感正文。

- AI 生成结果标记来源、模型信息、生成时间和审核状态。

- AI 自动审核或自动评分不得绕过教师确认等既定业务规则。

## 13.3 数据备份与恢复

- MySQL、MongoDB 等持久数据制定备份与恢复方案。

- RustFS 对象数据和 MySQL 文件元数据应协调备份。

- Elasticsearch 和 Milvus 索引应具备重建能力或快照策略。

- RabbitMQ 消息持久化、队列策略和死信处理应纳入运维方案。

- 定期进行恢复演练，而不只是检查备份文件是否存在。

# 附录 B：实施原则总结

- 先明确业务边界，再设计数据结构；先完成基础平台，再逐步启用 AI 和复杂教学功能。

- Java 管理正式教学业务和权限；Python 执行 AI 计算，不越权写入核心业务数据。

- MySQL 是正式业务事实来源；ES、Milvus 是派生检索索引；Redis 是缓存；MongoDB 保存适合文档型结构的数据。

- RustFS 保存文件对象；MySQL 保存文件元数据和授权关系。

- RabbitMQ 承担异步任务通信，重要事件采用事务发件箱、幂等消费和失败重试。

- 所有 AI 检索和文件访问必须遵循用户、院系、课程和资源授权范围。

- 模块化单体不是无边界的大单体；必须通过公开接口、事件和数据归属维持模块隔离。

- 设计模式服务于业务变化，不以复杂度和模式数量作为目标。
